Non-Functional Requirements (NFRs)
Non-functional requirements specify the quality attributes, system qualities, and operational constraints under which the system must function.

Security and Privacy: Focuses on data protection and authorization. The system must restrict unauthorized access to sensitive data (e.g., implementing Row-Level Security in the database).

Reliability and Availability: Ensures continuous system uptime and safe operation without failure (e.g., high availability for clinical monitoring and physical obstacle avoidance).

Efficiency (Performance): Defines system speed and resource usage under workload constraints (e.g., maintaining low-latency response times and real-time data updates).

Usability (Ergonomics): Measures how user-friendly, accessible, and intuitive the software is (e.g., a modern minimalist UI and voice interaction for users with limited mobility).

Extensibility: Measures how easily new features, components, or AI models can be integrated into the existing software architecture without breaking existing functionality.

Maintainability: Refers to how easily developers can update, debug, or refactor the system (e.g., clear code documentation for functions and core modules to aid future audits).

Scalability: The system's capability to handle increasing workloads, data volume, or concurrent user traffic seamlessly (e.g., horizontally scaling backend microservices during peak usage).

Interoperability: The ability of the application to connect, exchange data, and integrate smoothly with third-party APIs, legacy software, or external hardware systems.

Portability & Compatibility: The ease with which the application can run across multiple operating systems, hardware platforms, web browsers, or containerized environments (e.g., Docker runtime compatibility).

Robustness (Fault Tolerance): The system's ability to handle unexpected inputs, component failures, or network disruptions gracefully without causing a total crash.

Recoverability & Resiliency (Disaster Recovery): The system's capability to restore data and resume normal operations quickly following a major system crash or outage.

Testability: The degree to which software components can be isolated and verified through automated unit, integration, and performance testing pipelines.

Compliance & Regulatory: Adherence to legal standards, security regulations, and domain-specific privacy laws (e.g., GDPR for data privacy or HIPAA for medical data).

Auditability & Logging: The capability to capture structured logs and audit trails of user actions and internal system processes for troubleshooting and security monitoring.

Quick Reference Tip for Presentations/Reports
Pro Tip: In software architecture, NFRs are often referred to as the "-ilities" (Scalability, Maintainability, Usability, Availability, Reliability, Interoperability, Testability). Grouping them into Security, Performance, Usability, and Architecture makes them very easy to defend in an academic or technical presentation!

Foundations
Embedding — semantic representation from a neural network (captures meaning).
Vectorization — any text-to-number conversion, including non-semantic methods (TF-IDF, one-hot).
Embedding Model — converts text → vectors.
LLM — generates text from text.
Dense Vector — mostly non-zero values; neural, semantic.
Sparse Vector — mostly zero values; keyword-based, exact-match.
Search & Retrieval
Similarity — mathematical closeness in vector space (score).
Relevance — actual usefulness for answering the query.
Semantic Search — search by meaning; can use vectors, keywords, synonyms, query rewriting.
Vector Search — specific technique using embedding vectors + similarity metrics.
Query Embedding — embedding of the user's question; done at query time, must be fast.
Document Embedding — embedding of knowledge-base chunks; done offline, can be higher quality.
Top-K Retrieval — always returns exactly K results, regardless of quality.
Threshold Retrieval — returns only results above a score cutoff; can return zero.
Metadata Filtering — filter by structured fields (date, category, author); exact, fast.
Semantic Filtering — filter by meaning/content similarity; fuzzy, scored.
Data Structure
Chunk — a retrieval-sized piece of a document, may overlap, links back to parent.
Document — the original complete source file.
Chunking Strategy — the splitting method/logic (semantic, paragraph, sliding window).
Chunking Size — target chunk length (tokens/characters).
Index — the search structure (e.g., HNSW, IVF) for fast retrieval.
Database — storage system holding indices, metadata, documents.
Result Refinement
Re-ranking — reorder results using a different, more sophisticated model.
Re-scoring — recalculate scores with the same method or simple rule adjustments.
Filtering — remove results not meeting criteria (reduces count).
(Note: Reranking ≠ Filtering — reranking keeps the same count, just reorders.)
Performance & Timing
Latency — time waiting before processing starts (network/queue delay).
Response Time — total time from request to full answer (latency + processing).
Cold Start — index exists but not yet loaded in memory; first query is slow.
Empty Index — no documents indexed yet; can't answer anything.
Indexing Time — offline: chunking, embedding, storing documents.
Inference Time — per-query: embedding query, searching, generating answer.
Context Window — model's fixed maximum token capacity.
Context Length — actual tokens used in a given request.
Quality & Evaluation
Precision — of retrieved results, how many were relevant.
Recall — of all relevant docs that exist, how many were retrieved.
Hallucination — LLM invents info not present in retrieved context.
Incorrect Retrieval — wrong docs retrieved, but LLM used them faithfully.

STT (Speech-to-Text / ASR) — Core Concepts
Acoustic Model — maps audio features to phonemes/sub-word units.
Language Model (LM) — predicts likely word sequences; helps decode ambiguous audio.
Feature Extraction — converts raw waveform into representations (MFCC, mel-spectrogram, filterbank energies).
VAD (Voice Activity Detection) — detects presence/absence of speech in an audio stream.
Endpointing — decides when a user has finished speaking (silence/pause detection) to close the turn.
Diarization — determines "who spoke when" by segmenting and labeling speakers.
CTC (Connectionist Temporal Classification) — training/decoding method aligning audio frames to output tokens without needing exact frame-level labels.
Forced Alignment — aligns known transcript text to exact timestamps in audio.
Beam Search Decoding — keeps top-N candidate hypotheses during decoding instead of only the single best, improving accuracy.
N-best List / Lattice — set of alternative transcription hypotheses with scores.
Partial vs Final Transcript — partial = live, unstable, updated as more audio arrives; final = confirmed, stable segment.
Inverse Text Normalization (ITN) — converts spoken form to written form (e.g., "twenty dollars" → "$20").
Wake Word Detection — lightweight always-on model detecting a trigger phrase before full STT activates.
Confidence Score — model's certainty per word/segment; used to flag likely errors.
STT — Metrics & Formulas
WER (Word Error Rate) — word-level transcription accuracy. WER = (S + D + I) / N S = substitutions, D = deletions, I = insertions, N = total words in reference. Computed via Levenshtein (edit distance) alignment.
CER (Character Error Rate) — same formula as WER but at character level; more forgiving for morphologically rich languages or minor spelling variants.
MER (Match Error Rate) — accounts for insertions differently: MER = (S + D + I) / (N + I). Bounded between 0 and 1, unlike WER.
WIL (Word Information Lost) — estimates the proportion of word information incorrectly carried over; approximates 1 − (precision × recall) of word matching.
DER (Diarization Error Rate) — speaker attribution accuracy. DER = (False Alarm + Missed Detection + Speaker Confusion) / Total Reference Speech Time
RTF (Real-Time Factor) — processing speed relative to audio duration. RTF = Processing Time / Audio Duration RTF < 1 = faster than real-time (required for live voice agents); RTF > 1 = slower than real-time.
Latency (STT) — time from end of speech (or start of audio chunk, in streaming) to transcript availability.
TTS (Text-to-Speech) — Core Concepts
Grapheme-to-Phoneme (G2P) — converts written text into phoneme sequences for pronunciation.
Text Normalization — expands numbers, dates, abbreviations, symbols into speakable form (inverse of ITN).
Prosody — pitch, stress, rhythm, and intonation patterns applied to synthesized speech.
F0 / Pitch Predictor — predicts fundamental frequency contour controlling perceived pitch.
Duration Predictor — predicts how long each phoneme/frame should last.
Mel-Spectrogram Generation — intermediate acoustic representation predicted from text before waveform synthesis.
Vocoder — converts mel-spectrogram (or other acoustic features) into a raw audio waveform (e.g., WaveNet, HiFi-GAN, WaveGlow).
Alignment (Attention-based vs Duration-based) — attention-based models (e.g., Tacotron) learn text-audio alignment implicitly; duration-based models (e.g., FastSpeech) use explicit duration predictors for faster, more stable synthesis.
Autoregressive vs Non-Autoregressive TTS — autoregressive generates audio sequentially frame-by-frame (higher quality, slower); non-autoregressive generates in parallel (faster, better for real-time/streaming).
Speaker Embedding / Voice Cloning — vector representation of a speaker's voice characteristics used to condition synthesis toward a target voice.
SSML (Speech Synthesis Markup Language) — markup for controlling pauses, emphasis, pronunciation, and pacing in synthesized speech.
Streaming / Chunked Synthesis — generating and emitting audio in small chunks as they're ready, instead of waiting for the full utterance.
TTS — Metrics & Formulas
MOS (Mean Opinion Score) — subjective human-rated naturalness/quality score, typically 1–5 (averaged across listeners).
MCD (Mel-Cepstral Distortion) — objective distance between reference and synthesized speech in the cepstral domain. MCD = (10 / ln10) × √(2 × Σ(mc_i − mc'_i)²) Lower MCD = closer to reference voice.
PESQ (Perceptual Evaluation of Speech Quality) — objective intelligibility/quality metric, output range roughly −0.5 to 4.5.
STOI (Short-Time Objective Intelligibility) — objective metric estimating speech intelligibility, especially under noise/distortion.
RTF (Real-Time Factor) — same formula as STT, applied to synthesis: RTF = Synthesis Time / Output Audio Duration.
TTFB / TTFT (Time To First Byte / First Token) — latency from synthesis request to the first audio chunk being emitted; critical for perceived responsiveness in streaming voice agents.
Shared Signal Processing Concepts
Sample Rate (Hz) — number of audio samples per second (e.g., 16 kHz, 44.1 kHz).
Bit Depth — number of bits per audio sample, determines dynamic range resolution.
Frame Size / Hop Length — window size and stride used when slicing audio for feature extraction.
FFT / STFT (Fast Fourier Transform / Short-Time Fourier Transform) — converts time-domain audio into frequency-domain representation, frame by frame.
Mel Scale / Mel Filterbank — frequency scale approximating human pitch perception, used to compress spectrograms into perceptually relevant bands.
SNR (Signal-to-Noise Ratio) — ratio of desired signal power to background noise power, usually in dB: SNR(dB) = 10 × log10(P_signal / P_noise).
Echo Cancellation / Noise Suppression — preprocessing steps removing acoustic echo and background noise before STT.
Codec — audio compression/encoding format for transmission (e.g., Opus, PCM, G.711).
Jitter Buffer — buffer smoothing out network timing variability in streamed audio.
End-to-End Voice Agent Latency Chain

Relevant when reporting "real-time" performance — total perceived latency is the sum of each stage, not any single component: Total Latency ≈ VAD/Endpointing + STT Latency + RAG Retrieval + LLM Generation (or TTFT) + TTS TTFB + Network/Jitter Each stage can be optimized independently (e.g., streaming STT + streaming TTS reduces perceived latency even if total processing time is unchanged).

# Authentication, Authorization and Portal Security

## 1. Authentication architecture

The platform should use a centralized authentication mechanism for both types of users:

* **Client**
* **Administrator / Supervisor**

Authentication answers:

> **"Who is this user?"**

Authorization then determines:

> **"What is this user allowed to access?"**

The client and administrator do not need completely separate authentication systems. They can share the same identity/authentication layer while being redirected to different portals according to their role.

The architecture is:

```text
                    Authentication Service
                            │
                    Login / Verification
                            │
                    Authenticated Session
                            │
                 ┌──────────┴──────────┐
                 │                     │
              CLIENT                ADMIN
                 │                     │
          Client Portal          Admin Dashboard
                 │                     │
        Voice Agent + Account    Management + Monitoring
```

---

## 2. Client authentication

The client accesses the **Client Portal**.

A simple flow is:

```text
Client
  ↓
Login / Phone verification
  ↓
Authenticated session
  ↓
Client Portal
  ↓
Voice Agent + Account
```

The client's identity should be associated with their account/customer profile.

For a telecom platform, phone-number verification is particularly useful because the caller's phone number can later be associated with the authenticated customer profile.

The client portal can provide:

* Start/interact with the voice agent
* View their account information
* View relevant conversations/history
* View their requests/tickets
* Access customer-related services
* Manage their own profile where permitted

The client must only be able to access **their own data**.

For example:

```text
Client A → Client A data ✓
Client A → Client B data ✗
```

This requires server-side ownership checks; hiding information only in the frontend is not sufficient.

---

## 3. Administrator authentication

Administrators access a separate **Admin Dashboard**.

The flow is:

```text
Administrator
      ↓
Login
      ↓
Authentication verification
      ↓
Authenticated admin session
      ↓
Admin Dashboard
```

The backend must verify the authenticated identity before granting access.

The current implementation must NOT rely on a client-controlled header such as:

```text
X-Role: administrateur
```

as proof of identity.

A user must first be authenticated, and the backend must determine the user's role from trusted authentication/session information.

---

## 4. Role-Based Access Control (RBAC)

After authentication, the backend determines the user's role.

At minimum:

```text
CLIENT
ADMIN / SUPERVISOR
```

Authentication and authorization must remain separate:

```text
Authentication
"What is your identity?"
        ↓
Authorization
"What can you access?"
```

Example:

| Resource                 | Client | Admin |
| ------------------------ | -----: | ----: |
| Own profile              |      ✓ |     — |
| Own account              |      ✓ |     — |
| Voice agent              |      ✓ |     — |
| Own conversations        |      ✓ |     — |
| Other customers          |      ✗ |     ✓ |
| Customer management      |      ✗ |     ✓ |
| Conversations monitoring |      ✗ |     ✓ |
| Tickets management       |      ✗ |     ✓ |
| System metrics           |      ✗ |     ✓ |
| Admin dashboard          |      ✗ |     ✓ |

The backend must enforce these permissions on every protected API endpoint.

---

## 5. Secure session model

After successful authentication, the system creates an authenticated session.

Conceptually:

```text
Login
  ↓
Credentials / verification
  ↓
Identity validated
  ↓
Secure session/token
  ↓
Authenticated API requests
```

For a web application, the preferred simple approach is a secure server-managed session or secure HTTP-only cookie.

The browser should not be trusted to declare its own role.

Security properties should include:

* HTTPS/TLS in deployed environments
* Secure cookies
* `HttpOnly` cookies
* Appropriate `SameSite` policy
* Session expiration
* Logout/session invalidation
* Protection against session manipulation
* Server-side authorization checks

Sensitive authentication information must never be exposed in frontend code or stored insecurely.

---

## 6. Admin Dashboard security

The Admin Dashboard should have two security layers.

### Frontend protection

The frontend checks whether the user has an authenticated session and the required role before displaying protected pages.

### Backend protection

The backend independently verifies:

```text
Request
 ↓
Authenticated?
 ├── No → 401 Unauthorized
 └── Yes
      ↓
Required role?
 ├── No → 403 Forbidden
 └── Yes → Process request
```

This backend verification is mandatory because users can bypass frontend restrictions and call APIs directly.

Therefore:

> **Frontend protection improves UX; backend authorization provides the actual security boundary.**

---

## 7. Client portal security

The same principle applies to the Client Portal.

A client request should be checked against the authenticated customer's identity.

For example:

```text
Authenticated as Customer A
        ↓
GET /customers/A/conversations
        ↓
Ownership check
        ↓
Allowed
```

But:

```text
Authenticated as Customer A
        ↓
GET /customers/B/conversations
        ↓
Ownership check
        ↓
403 Forbidden
```

This prevents horizontal privilege escalation between customers.

---

## 8. Sensitive voice-agent operations

Authentication of the portal user is not enough for sensitive telecom operations.

The existing voice-agent security architecture should remain:

```text
Authenticated Customer
        ↓
Identity Verification / Step-up verification
        ↓
Decision
        ↓
Policy
        ↓
Execution
        ↓
Audit
```

This is particularly important for operations such as:

* Payments
* Top-ups
* SIM replacement
* Account modifications
* Provisioning operations
* Other sensitive customer actions

The platform should never execute a sensitive action only because the user is logged into the portal.

The existing Decision → Policy → Execution invariant must remain enforced.

---

## 9. Audit and security monitoring

Administrative and sensitive operations should be auditable.

The system should record relevant information such as:

* Authenticated user identity
* User role
* Action performed
* Target resource
* Timestamp
* Result
* Authorization decision
* Sensitive-operation verdict
* Relevant audit identifier

Sensitive data should remain protected and masked where necessary.

This allows supervisors/security personnel to answer:

> Who performed this action, when, on which resource, and what was the result?

The existing platform already has an audit-oriented architecture and should preserve it rather than introducing a separate logging mechanism.

---

## 10. Final architecture

The resulting security model can be summarized as:

```text
                         USER
                           │
                     Authentication
                           │
                 ┌─────────┴─────────┐
                 │                   │
              CLIENT               ADMIN
                 │                   │
          Client Portal        Admin Dashboard
                 │                   │
                 └─────────┬─────────┘
                           │
                    Authenticated API
                           │
                  Backend Authorization
                           │
              ┌────────────┴────────────┐
              │                         │
        Own customer data        Admin resources
              │                         │
              └────────────┬────────────┘
                           │
                  Voice Agent Services
                           │
              Sensitive operation?
                       /       \
                     No         Yes
                     │           │
                   Execute   Identity verification
                                ↓
                             Decision
                                ↓
                              Policy
                                ↓
                             Execution
                                ↓
                              Audit
```

## 11. What should be reported as the final security model

The final report should describe the platform as implementing:

* Centralized user authentication
* Separate Client Portal and Admin Dashboard
* Role-Based Access Control
* Server-side authorization
* Client data ownership isolation
* Secure authenticated sessions
* `401` for unauthenticated requests
* `403` for authenticated but unauthorized requests
* Protection against forged client-side roles
* Additional identity verification for sensitive telecom actions
* Decision → Policy → Execution enforcement
* Idempotent sensitive operations
* Auditing of administrative and sensitive actions
* PII protection and masking
* Fail-closed behavior when authorization/security information is missing or invalid

The important distinction is that **portal authentication controls access to the platform, while the existing identity-verification + Decision + Policy + Execution chain protects sensitive telecom operations inside the platform.**
