# Previous Reports — Academic Writing & Methodology Reference Analysis

The files in this folder contain **older academic/PFE reports**.

These reports are NOT our report.

Their subjects, technologies, architectures, organizations, methodologies, conclusions, and technical content are different from our project.

Therefore, **do not copy their content or structure blindly**.

The purpose of these reports is to learn from them as **academic writing references**.

---

# 1. Main Objective

Study the previous reports to understand:

* how a professional academic report is written
* how ideas are introduced
* how technical explanations are formulated
* how paragraphs are structured
* how long paragraphs tend to be
* how sections and subsections are organized
* how transitions between ideas are written
* how methodologies are presented
* how technical work is described academically
* how results are introduced and interpreted
* how conclusions are written
* how the authors maintain a professional academic tone
* which pronouns and grammatical constructions they use
* how they describe their own work
* how they refer to the reader, project, system, team, or authors
* what recurring sections appear across different reports
* what recurring writing patterns appear across different reports

The goal is to understand **how a strong academic report should sound and feel**, not to reproduce any particular report.

---

# 2. Extremely Important: Each Report Is Different

Each old report may use a different methodology, for example:

* Scrum
* Kanban
* CRISP-DM
* Iterative and Incremental
* Waterfall
* Agile variants
* other project-specific methodologies

Each report may also concern a completely different:

* domain
* application
* architecture
* technology
* problem
* research objective
* development process
* evaluation method

Therefore:

> **Never assume that the methodology, chapter structure, terminology, or technical organization of one report is automatically appropriate for our report.**

Instead, identify:

**What is specific to that report?**

and separately:

**What is a generally reusable academic-writing practice?**

---

# 3. Separate CONTENT From WRITING STYLE

This distinction is essential.

For every report, mentally separate:

### A. Project-specific content

Things we should NOT copy:

* project subject
* application domain
* technologies
* architecture
* methodology-specific details
* datasets
* implementation details
* results
* conclusions
* terminology specific to their project

### B. Reusable academic patterns

Things we SHOULD study:

* writing tone
* paragraph construction
* sentence structure
* vocabulary level
* explanation style
* transitions
* section introductions
* technical descriptions
* argumentation
* methodological presentation
* result interpretation
* conclusion style
* use of pronouns
* consistency
* academic formality

The second category is the primary purpose of this analysis.

---

# 4. Analyze the Writing Tone

Study how the authors communicate.

Determine whether the reports generally use:

* formal academic language
* neutral technical language
* objective language
* explanatory language
* analytical language
* first-person plural
* first-person singular
* passive voice
* impersonal constructions
* direct technical statements

Pay particular attention to recurring formulations.

For example, identify how authors typically write sentences equivalent to:

* introducing a problem
* explaining its importance
* presenting an objective
* introducing a methodology
* presenting an architecture
* describing an implementation
* explaining a figure
* interpreting a table
* presenting an experiment
* discussing results
* transitioning to the next section
* concluding a chapter

Do not copy exact sentences.

Extract the **writing pattern behind them**.

---

# 5. Analyze Sentence Construction

Study:

* average sentence length
* short vs long sentences
* sentence complexity
* use of subordinate clauses
* use of technical terminology
* balance between explanation and concision
* how definitions are introduced
* how cause/effect relationships are expressed
* how comparisons are expressed
* how technical decisions are justified

Determine what makes the writing sound academic rather than conversational.

Identify patterns such as:

> Context → problem → explanation → consequence → solution

or:

> Observation → analysis → decision → justification

or:

> Objective → method → result → interpretation

These patterns can later inspire our own writing.

---

# 6. Analyze Paragraph Construction

For each report, study how paragraphs are built.

Identify common patterns such as:

### Pattern A

Topic sentence → explanation → technical detail → conclusion

### Pattern B

Context → problem → consequence → proposed solution

### Pattern C

Claim → evidence → interpretation

### Pattern D

Concept introduction → definition → example → relevance to project

### Pattern E

Technical decision → alternatives → justification → selected solution

Determine:

* typical paragraph length
* how many ideas appear in one paragraph
* how paragraphs transition
* whether paragraphs are dense or concise
* how repetition is avoided

The objective is to learn how to construct **clear academic paragraphs**.

---

# 7. Analyze Section and Chapter Organization

Across all old reports, identify recurring structural elements.

Some may repeatedly contain sections such as:

* Introduction
* General Context
* Problem Statement
* Objectives
* Existing Solutions
* State of the Art
* Requirements
* Methodology
* Analysis
* Design
* Architecture
* Implementation
* Testing
* Evaluation
* Results
* Discussion
* Conclusion

Do NOT automatically copy these sections.

Instead:

2. Determine why they appear repeatedly.
3. Determine what academic purpose they serve.
4. Determine whether that purpose applies to our report.
5. Decide later whether our report needs an equivalent section.

The objective is to recognize **useful academic structures**, not force our project into an old report's template.

---

# 8. Analyze Methodology Presentation

Because different reports use different methodologies, this is especially important.

Study how each report presents its methodology.

For example:

* why the methodology was selected
* how its principles are introduced
* how phases are explained
* how project activities are mapped to the methodology
* how iterations/sprints/phases are documented
* how deliverables are presented
* how methodology-specific vocabulary is introduced
* how methodology diagrams are explained

Do NOT conclude:

> "Our project must use the same methodology."

Instead conclude:

> "This is how an academic report explains a chosen methodology."

Later we will adapt the writing approach to **our actual methodology**.

---

# 9. Analyze How Technical Content Is Explained

Study how the reports explain technical subjects to a reader who may not know the system beforehand.

Look at:

* definitions
* architecture explanations
* technology introductions
* component descriptions
* workflow explanations
* diagrams
* tables
* implementation explanations
* technical decisions
* comparisons
* limitations

Pay attention to the progression:

**What is it?**

→ **Why is it relevant?**

→ **How does it work?**

→ **How is it used in the project?**

This progression can be particularly useful for our own technical chapters.

---

# 10. Analyze Figure and Table Explanations

Do not only inspect the figures/tables themselves.

Study the surrounding prose.

Understand how authors:

* introduce a figure
* refer to it before showing it
* describe what it represents
* explain its important elements
* interpret the figure
* transition after the figure

Do the same for tables:

* why the table is introduced
* what the reader should notice
* how comparisons are explained
* how conclusions are drawn from a table

Learn the writing pattern, not their actual content.

---

# 11. Analyze Repetition Across Reports

One of the most valuable things to identify is what appears repeatedly.

Across the collection, identify:

* recurring sections
* recurring introductions
* recurring transitions
* recurring methodological explanations
* recurring paragraph structures
* recurring conclusion patterns
* recurring terminology patterns
* recurring pronoun usage
* recurring ways of presenting technical work
* recurring ways of presenting results

These repetitions may reveal **the conventions of academic/PFE writing**.

Create a distinction between:

### Strong recurring convention

Something that appears consistently and is likely a useful academic practice.

### Methodology-specific convention

Something repeated because several reports use the same methodology.

### Project-specific convention

Something that exists only because of a particular project's subject.

### Personal author style

Something unique to one author and not necessarily worth adopting.

---

# 12. Analyze Pronouns and Author Voice

Pay special attention to how authors refer to themselves and their work.

Study the use of:

* “we”
* “we propose”
* “we developed”
* “we implemented”
* “we selected”
* “the system”
* “the proposed solution”
* “the developed application”
* passive voice
* impersonal forms

Determine which style produces the strongest academic tone.

Do not blindly copy one report.

Infer a **consistent voice** that can be used across our entire report.

The final report must avoid switching randomly between:

* “we”
* “I”
* “the team”
* “the developer”
* “the authors”
* passive voice

unless there is a deliberate stylistic reason.

---

# 13. Analyze Academic Vocabulary

Identify the vocabulary level used in strong reports.

Look for patterns in words used to:

* introduce objectives
* justify decisions
* compare solutions
* describe processes
* present results
* explain limitations
* formulate conclusions
* introduce recommendations

Identify useful categories of academic expressions, but do not create a giant list of copied phrases.

Focus on the **style and function** of the language.

---

# 14. Analyze Transitions

Study how reports move between:

* paragraphs
* sections
* subsections
* chapters
* methodological stages
* technical components
* results
* discussions
* conclusions

Identify how writers avoid abrupt transitions.

Understand patterns such as:

**Previous concept → limitation → next concept**

**Problem → methodology**

**Methodology → implementation**

**Implementation → evaluation**

**Result → interpretation**

The final report should feel like **one continuous argument**, rather than a collection of disconnected sections.

---

# 15. Analyze What Makes the Reports Weak Too

Do not assume everything in these reports is good.

Identify:

* overly long paragraphs
* unnecessary repetition
* vague statements
* weak transitions
* redundant sections
* unnecessary technical details
* poorly explained figures
* tables without interpretation
* weak conclusions
* excessive passive voice
* informal expressions
* unsupported claims
* repetitive introductions
* sentences that are too complicated
* sections that exist only because of tradition rather than necessity

These reports should provide both:

**examples to learn from**

and

**mistakes to avoid.**

---

# 16. Build a Reusable Academic Writing Profile

After analyzing the reports, create a concise profile describing the writing style we want for our report.

The profile should define:

### Tone

Example:
Professional, academic, objective, technically precise.

### Voice

Determine the preferred pronoun strategy.

### Sentence Style

Define an appropriate balance between concise and complex sentences.

### Paragraph Style

Define how many ideas a paragraph should normally contain and how ideas should progress.

### Technical Style

Explain concepts before relying on them.

### Evidence

Claims should be supported by references, implementation evidence, experiments, or project facts whenever appropriate.

### Transitions

Sections should connect logically.

### Conclusions

Do not merely repeat the section. Explain what was established and why it matters.

# Final Principle

**Learn from the old reports, but do not become limited by them.**

We want to extract their best academic practices, combine them with the requirements of our own project and the LaTeX template, and produce a report that is:

> **academically credible + technically rigorous + exceptionally clear + coherent + professional + well structured + more impressive than the reference reports.**

# Supervisor-Recommended Report Structure — Mandatory Reference

This folder contains an additional folder with a **report structure recommended by our academic supervisor**.

This structure must be treated as a **high-priority and trusted academic reference** for our report.

It was recommended by an experienced academic supervisor and represents a structure that has already been reviewed and considered appropriate for our academic context.

Therefore, it should **not** be treated like the older example reports.

---

# 1. Priority of This Structure

The supervisor-recommended structure has strong authority for our report organization.

When deciding the report structure, use the following priority:

1. Explicit supervisor requirements and recommendations
2. University / academic requirements
3. Existing LaTeX template structure
4. Project-specific needs
5. Academic patterns learned from previous reports
6. Personal suggestions or stylistic preferences

Do not let an older report override an explicit supervisor recommendation.

---

# 2. Purpose of This Folder

The purpose of this folder is to understand and preserve the recommended structure.

Study it carefully and identify:

* chapter organization
* section organization
* subsection hierarchy
* expected progression of ideas
* expected academic narrative
* recommended order of topics
* expected methodology placement
* expected technical content
* expected implementation sections
* expected evaluation/results sections
* expected conclusion structure
* expected annex organization

The objective is not merely to copy the headings.

Understand **why this structure was recommended**.

# 3. Treat It as the Structural Baseline

When planning our real report, use the supervisor's structure as the **baseline architecture**.

* our project's actual subject

Any significant deviation should be justified.

Do not reorganize the report simply because another structure looks more convenient.

# 9. Important Interpretation Rule

The supervisor's recommendation should be treated as **trusted academic guidance**, but not as permission to invent content.

A recommended section does not mean we should fill it with assumptions.

For every section:

* use verified project information
* identify missing information
* request/locate evidence when necessary
* mark unknown information explicitly
* never fabricate results, architecture, methodologies, experiments, or conclusions

A strong structure with fabricated content is worse than an incomplete structure with verified content.
